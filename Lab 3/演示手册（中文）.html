一 演示前准备

1 运行目录和启动方式

本机已有依赖和配置的运行目录是 PlugPlan SG；Lab 3/application skeleton 是提交源码目录。当前界面、计算夹具、引擎和服务代码两处一致；提交目录没有 credentials.env。不要把只有 TODO 的 AI-Generated-Skeleton.zip 当作可运行应用。

cd 'D:\Downloads\SC2006-SCE3-04\PlugPlan SG'
pnpm build
pnpm start

# 浏览器打开（主线直接进入 Demo 模式）
http://127.0.0.1:3000/?mode=demo

先停掉使用同一目录的开发服务器再 build。Node.js 需 ≥22.12，pnpm 版本为 11.25.0。若在另一台电脑从提交目录启动，按该目录 README 安装依赖、填写自己的 credentials.env，并应用已有 Supabase 迁移；不要临场新建数据库或重复执行已应用的迁移。

2 账号和浏览器安排

账号／会话用途与限额安排
Driver A主线、图片、重复报告、Reject/Expire 用的报告。建议控制在 4 次有效提交尝试以内，留出余量。
Driver B辅助报告：Merge 两条 + 可选“无备选”三条，共 5 次。也可作为另一个所有者验证数据隔离。
Driver C限流专用新账号；在开始前保存车辆并建立一份基线计划，然后专门尝试 6 次提交。
额外 Driver（选做）若要额外展示同站两条独立故障支持，用另一新 Driver 建两条报告，避免 B 超过每小时 5 次。
Moderator M1 / M2M1 是主审核会话；M2 是独立浏览器会话，用于 revision 冲突。可同一 Moderator 号分别登录两个隔离浏览器会话，也可用两个已配置的 Moderator 号。

同一浏览器普通标签页共享登录状态，不能靠两个标签页分别保留 Driver 和 Moderator。可用 Chrome 正常窗口作 A、Edge 正常窗口作 M1、Chrome 无痕作 M2／辅助 Driver；同一组无痕窗口通常也共享会话，换角色要先退出。Moderator 需事先配置，公开注册界面不能自行选择此角色。

3 预演和复位

  • 确认 Driver 能登录并保存车辆，Moderator 能读取报告列表；准备实际可用的账号，不把密码放进讲稿或投影。
  • 演示前 30-60 分钟新建需要审核的报告，避免前一天的 24 小时报告已经到期。重复尝试也计入每账号每小时 5 次，预演不要耗尽正式账号额度。
  • 主线前，在 Moderator 确认 Demo Fast Charge、Demo Value Charge、Demo Reported Fault 没有遗留的有效 Verified 故障。只处理自己组明确标记的演示报告；若有其他人的有效报告，先协调独立演示环境。
  • 准备好 demo-support/demo-evidence.png（合成演示图片）和 demo-support/invalid-upload.svg（不支持的图片格式）。
  • 先完成一次从 Pending → Verified → Driver 刷新 → Resolve → Driver 刷新的预演；确认结束后基线恢复 3 项。

UC-01 账户访问

主流程：Driver 和 Moderator 登录

  1. 打开访问页，填演示 Driver 邮箱和密码，点 Sign in。看到 Driver 菜单：Plan a journey、Saved plans、Your vehicle、Your reports。首次没有车辆时进入 Your vehicle。
  2. 在独立浏览器登录 Moderator。看到 Report review 和 All reports，不能把 Driver 菜单当作审核入口。
  3. 讲解：“认证由 Supabase 管理，工作区和操作权限依据服务端保存的角色；前端隐藏按钮只是第一层，服务端也检查。”
Flow具体操作应看到／恢复方式
UC-01.A1 注册Create an account → 新邮箱；密码至少 10 字符，含字母和数字 → Create Driver account。创建 Driver。本项目演示设置是不要求邮箱确认；预演时核实该设置。若出现确认邮件提示，先完成账号确认，不把待确认账号当作登录成功。
UC-01.A2 退出右上角 Sign out；若有未保存改动，先处理确认框。返回访问页；再次进入工作区需要有效会话。退出放在所有业务演示结束后。
UC-01.E1 无效凭据在退出状态输入错误密码后 Sign in。通用错误，不透露账号是否存在；改回正确密码继续。若要展示 inactive 分支，需事先有专用禁用账号，不临场禁用主账号。
UC-01.E2 认证不可用访问页已加载后，DevTools Network 设 Offline，再点 Sign in；演完立即切回 Online。受控浏览器网络失败，无新会话；展示重试。该操作不代表 Supabase 实际停机。

UC-02 管理车辆资料

主流程：创建、修改、重新读取

  1. 点 Your vehicle，按固定车辆表填写，点 Save vehicle。展示成功提示和返回行程页。
  2. 再进 Your vehicle，确认参数仍在；把 Vehicle name 改为 Demo EV updated，保存并重新打开确认。只改名字不影响基准计算，之后可改回 Demo EV。
  3. 讲解：“同一 Driver 只有一个当前车辆资料；每个历史计划版本保存当时的假设，后续改车不会重写旧结果。”
Flow具体操作应看到／恢复方式
UC-02.A1 放弃编辑改车辆名称但不保存 → 点 Saved plans → 确认离开 → 再进 Your vehicle。显示最后保存的名字，不是刚才未保存的值。没有独立 Cancel 按钮。
UC-02.A2 删除留到收尾：先有一份保存计划，再 Delete vehicle → 确认。当前 profile 删除；Plan a journey 要求设置车辆；旧计划仍可打开并显示旧假设。表单可能显示默认值，这不等于自动保存了新 profile。
UC-02.E1 无效字段容量输入 9 或清空必填项后 Save vehicle；再取消所有 Compatible plugs 后保存。数值可能先被浏览器原生约束拦住；无插头等服务端错误显示字段提示。要明确展示服务端 400，用附录的无效 profile 请求。恢复容量 60 和两种插头。
UC-02.E2 保存失败附录工具执行 pp.failNext("profile.save")；修改名字并 Save vehicle。受控 503，输入保留；请求未到后端。工具自动恢复后重试一次应成功。这展示界面失败恢复，不伪称数据库崩溃。

UC-03 创建充电计划

主流程：固定示例创建并解释计算

  1. 确认车辆已保存。在顶部选 Demo fixtures → Use example journey；按行程表改为 18%、20:00、45 分钟充电、15 分钟绕行、Balanced 和自动目标。
  2. 点 Find charging options。看到 Your charging options、新保存的 Version 1、3 considered options 和来源标签 DEMO_FIXTURE。
  3. 指向第一张 Fast 卡片：到站 14.5%，自动目标约 26.4%，从充电桩取得约 7.9 kWh、约 4 分钟、约 S$4.37。说明目标是“够到终点并保留 20%”，不是一律充满。
  4. 展开 Assumptions & considerations；指出 90% 充电效率，采用车辆与桩额定功率的较小者，费用不含停车／占位等额外费用。
  5. 展开底部 excluded candidates，展示不兼容、不可达、营业时间、充电时间、绕行和占用等原因。
  6. 去 Saved plans 确认刚才的计划存在，再 Open plan 回来。记录它作为主线计划，后面重配和刷新都打开这同一份计划。
Flow可重复操作应看到／恢复方式
UC-03.A1 Demo显式选择 Demo fixtures 后创建，使用上面的固定数据。标记 DEMO_FIXTURE；仍经过账户保存、计算和报告过滤，不是静态截图。
UC-03.A2 多搜索结果已恢复有效 Live Token 后切 Live data，Starting from 输入有多个地址的关键词，如 Orchard；等待候选并选定一项。候选数量以真实搜索结果为准；必须点选候选而非只留输入文字。若没有多项，换较宽泛关键词；不用唯一结果冒充歧义选择。
UC-03.A3 手动目标恢复基线 → Set my own target → 60 → 计算。再可改为 90 演示高 SOC 提醒。60% 时通常剩 Fast 和 Reported Fault 两项，Value 因充电时间过长排除；卡片同时展示自动目标与手动目标。90% 展示超过 80% 的 taper 提醒。之后改回自动目标。
UC-03.A4 无需充电基线只把 Current battery 改为 100% → 计算。You’re good to go；解释直接行程后仍有足够储备，不强行推荐无意义充电。
UC-03.A4 无可行项另建基线，把 Maximum detour 改为 0；或自动目标改手动 20%。No suitable stop this time；展开排除原因。前者是绕行超限，后者是低于到终点加储备所需的目标。之后恢复基线。
UC-03.E1 无路线／快照在 Live 模式、有效地点输入下，上游实际返回错误且无可用缓存时再提交；预演保留该真实失败画面。不保存半成品版本，输入保留。具体可用缓存和失败安排见“Live 与缓存”；仅拦截浏览器 /api/app 不能证明上游分支。
UC-03.E2 状态与失败分别指向成功结果的来源标签和时间；发生 Live 请求错误时指出仍处于 Live data。不静默切 Demo。需要继续稳定主线时明确手动切 Demo，再重试；不能把这次切换说成自动缓存回退。

UC-04 查看和比较推荐

主流程：比较和选择

  1. Saved plans → Open plan，使用 3 项的基线计划。未勾选时点 Compare options，默认比较全部；Back to options 后勾选两项，按钮变为 Compare (2)，再次进入比较。
  2. 按相同列比较充电时间、总旅程时间、绕行、能量、目标 SOC、费用、可用率、解释与假设。Availability 是当前兼容接口的可用比例，不是未来成功概率。
  3. 点 Fast 的 Choose this stop（比较页为 Select charger）；回结果页看到 Selected。记下当前版本号。改选另一个当前推荐，版本号不变。
  4. 讲解：“偏好选择存放在计划层；没有预订、付款或排队位置。”最后为主线重新选 Fast。
Flow可重复操作应看到／恢复方式
UC-04.A1 仅一项Your vehicle 把 Minimum charger power 设为 110，保存；新建其余相同基线。只剩 Fast；比较按钮禁用并解释至少要两项。之后 Minimum charger power 恢复 0；旧单项版本保留其 110 假设。
UC-04.A2 未知价格基线改 Maximum detour=20、Ranking strategy=Fastest journey，其余不变。前三项包含 Demo Price Unavailable，费用显示 Price unavailable，不是 S$0；进入比较也保持未知。之后恢复 15 和 Balanced。
UC-04.A3 历史版本先完成一次 UC-05 重配，再用 Plan version 下拉框选旧版本。可看／比较旧证据；Choose this stop / Select charger 禁用。返回最新版本才能改选择。
UC-04.A4 更换选择当前版本先选 Fast，再选 Reported Fault，再改回 Fast。Selected 跟着改变，版本号不增加；不能通过再次点 Selected 来清空选择。
UC-04.E1 非本人／不存在Driver A 记录主线计划完整 ID；在 Driver B 的隔离窗口执行附录中的 plan.refresh 请求。真实 API 返回 404，不返回 A 的计划；正常 UI 也没有他人计划入口。使用随机有效 UUID 可演示“不存在”。
UC-04.E2 保存选择失败先已选 Fast；pp.failNext("plan.select") 后尝试选另一项。503 提示，原选择不变；恢复后刷新资料／重开计划核对，再正常改选。

UC-05 重新配置计划

主流程：编辑同一计划并保留历史

  1. 在主线计划点 Edit journey，把可用充电时间从 45 改为 60，点 Recalculate plan。注意按钮不是 Find charging options。
  2. 确认同一计划出现 Version n+1；切回 Version n，仍看到 45 分钟等旧输入和旧结果。
  3. 回最新版本，Edit journey 恢复 45，成功后再出现一个新版本。选择有效时可保留，否则清空；不要把“必定保留旧选择”当成无条件规则。
Flow具体操作应看到／恢复方式
UC-05.A1 策略变更点 Cheapest charging，再点 Fastest journey、Availability first、Minimum detour、Balanced。每次成功重算追加版本。Cheapest 的基线可首先出现 Value；其他策略如果排序相同也正常，不承诺每个标签一定换第一名。
UC-05.A2 取消Edit journey，改一项 → Cancel changes。回原结果，未新增版本、原输入保持；不是把旧版本覆盖掉。
UC-05.A3 原候选失效Edit journey 把最大绕行改为 0 → Recalculate plan。新版本无可行站并说明绕行超限；旧 15 分钟版本仍有候选。再 Edit journey 改回 15 恢复。
UC-05.E1 证据不可用实际 Live 上游失败且不能复用路线/站点证据时重配；界面恢复可另用 pp.failNext("plan.reconfigure")。真实后端失败不新增版本，旧版本仍在。受控 503 只演示请求失败界面；不要把它当缓存逻辑证明。
UC-05.E2 未保存离开编辑一项，点 Saved plans；先在浏览器确认框选择取消，再重试并确认离开。第一次保留草稿；第二次丢弃草稿。重新打开原计划看到已保存版本。

UC-06 刷新数据并选择备选

主流程：审核变化前后交叉演示

  1. Driver A 先在基线当前版本选 Fast，记下版本号；没有新 Verified 故障时点 Refresh data，观察新版本和原 Selected 保留。
  2. 按 UC-07 提交针对 Fast 的疑似故障报告；Pending 阶段刷新一次，确认 Fast 尚未被排除。
  3. 切到 Moderator，按 UC-08 Verify 该报告。Driver 回同一计划，保持 Demo fixtures，点 Refresh data。
  4. 预期新列表只剩 Reported Fault 和 Value，Fast 出现在排除说明中；旧选择清除，文字提示下一备选。点击下一备选的 Choose this stop 完成选择。系统不自动替用户选站。
  5. 再刷新一次，若该选择仍在列表，仍保持 Selected。然后 Moderator Resolve Fast 报告，Driver 再刷新，Fast 恢复候选。
  6. 切到故障标记出现之前的旧版本：旧结果仍可显示 Fast，这是历史证据，不表示当前过滤没有生效。回最新版本继续。
Flow操作位置预期／条件
UC-06.A1 缓存／过期Live 路线先成功预热，再观察同一路线策略重算的 CACHED；真实 provider 失败时仅在仍有可用服务端缓存下观察 STALE。必须看实际徽标、observed/retrieved 时间及警告。缓存属于服务端，Demo 不能代测；详见下一章。
UC-06.A2 原选择仍在没有新增故障且输入相同的基线选 Fast → Refresh data。新版本保留 Fast 的选择。
UC-06.A3 原选择失效上面的 Pending → Verify → Driver Refresh。清除 Fast 选择，提示下一备选，Driver 主动选择。
UC-06.A4 Demo 刷新确认 Demo fixtures 后 Refresh data。追加 Demo Fixture 新版本；不是向 LTA 查询最新状态。
UC-06.E1 刷新失败真实 Live provider 失败且无可用缓存时刷新；另可 pp.failNext("plan.refresh") 演示界面失败恢复。无新版本、旧结果可用；受控请求与真实 provider 失败分别说明。
UC-06.E2 无备选按“补充场景”把基线三项都审核为有效故障后，刷新此前已选 Fast 的同一计划。列表为空、选择清空、明确提示没有备选；不自动推荐已标故障站。随后 Resolve 本次三条报告并刷新恢复。

Live 数据 缓存和上游失败的演示

1 先恢复 Live 能力，再决定现场展示范围

  1. 在自己的 OneMap 账号取得有效 Token，更新 PlugPlan SG/credentials.env 的 OneMap_API；不要把 Token 放进讲稿、浏览器 URL 或截图。重新启动 Node 服务。
  2. 用有效 Supabase 登录，切 Live data。先搜索两个新地点并选候选，再创建计划。查看 /api/app 的真实成功或失败结果；不要以底图能加载来推断搜索、路由和 LTA 都可用。
  3. 成功后记录来源、时间戳、候选数。现场按真实结果讲解；Live 可能只有 0/1 项，不承诺也有三项。主线的“三选比较”仍使用明确标记的 Demo 基线。

2 CACHED 和 STALE 的条件不同

状态／场景准备与观察
LIVE取得可用实时站点和路线证据；显示何时观测／何时获取。仍可能受覆盖限制影响。
CACHED同一个 Node 进程先成功生成 Live 计划；保持相同起终点、满足路线与站点缓存时限，马上点策略标签重配。实际返回 CACHED 时展示来源时间不被假装更新。
STALE已有兼容的服务端缓存，随后真实 provider 获取失败或相关证据过期时，后端才可能带警告复用。要做确定的上游故障演示，需单独测试环境的 provider 故障控制和预热；当前产品没有此 UI 开关。
无可用缓存的失败新进程或未预热路线，真实 provider 返回错误／不可用时，显示明确失败，不偷偷切 Demo，不保存半个版本。
浏览器受控 503pp.failNext 只让指定业务请求在浏览器返回错误；它能演示输入保留／重试，但不能验证后端缓存、provider 超时预算或数据库事务。

如果没有事先准备好真实 STALE 结果，现场只讲清机制，不把该分支勾成“已现场验证”。可以保留预演时真实失败／缓存画面的截图和 Network 状态作补充。离线浏览器、过期 OneMap Token、LTA 上游异常是不同原因，讲解时按实际原因说明。

UC-07 提交充电桩问题报告

主流程：带图片提交 Pending 报告

  1. 在主线当前计划的 Demo Fast Charge 卡片点 Report an issue at this charger。核对站点／连接器是预填的，类别选 Suspected faulty connector。
  2. Issue details 输入“2026-10-29 演示：合成故障报告，无真实设备问题。”；上传 demo-evidence.png；点 Confirm & submit report。
  3. 看到 Your reports 中的新 Pending 报告、参考号与到期时间。打开 View report，再点 View evidence image 展示图片。
  4. 回 Saved plans → 原计划 → Refresh data。此时报告只 Pending，Fast 仍可推荐。讲解“用户报告不直接改变官方数据，也不直接排除站点”。
Flow具体操作应看到／恢复方式
UC-07.A1 不传图片对 Value 建 Blocked charging bay 报告，填写说明，不选图片。照常成为 Pending；这条可供 Moderator 演示 Reject。
UC-07.A2 重复同一站点、连接器、类别再次提交；也可在另一 Driver 上提交同一目标。显示已有报告的安全摘要，不新增报告；当前界面转到 Your reports 并弹出摘要，不会自动回推荐页。点 Done 后从 Saved plans 重新打开原计划。重复尝试会消耗一次额度。
UC-07.A3 运营商支持在真实 Live 推荐中找有已映射支持链接的运营商，打开报告表单并点官方支持链接，不提交报告。新标签打开官方支持页面；无新社区报告。Demo 站点无真实运营商链接，只能展示说明，不能假称成功跳转。
UC-07.E1 图片类型／大小先填写说明，选择 invalid-upload.svg；或选择实际超过 5 MiB 的图片，再尝试提交。不支持的类型／超大图片被拒绝，说明文字保留；改选 demo-evidence.png 后再试。
UC-07.E2 超限Driver C 建好计划后执行 pp.rateDemo()；第六次应显示真实 429。再从该账号界面提交一次。UI 显示可再次提交的 SGT 时间，草稿保留；没有新增超限报告。该账号一小时内不再用于其他报告演示。
UC-07.E3 上传／保存失败不传图片时 pp.failNext("report.create")，再提交。上传失败分支可对 Storage 上传请求做受控阻断后重试。提交失败保留输入。若真实网络中断导致结果不确定，先刷新 Your reports 确认是否已保存，再决定重试；不要盲目连点。

报告说明 UI 为 5-2,000 字符；支持 JPEG/PNG/WebP，最多 5 MiB。同一账号滚动一小时最多 5 次有效提交流程，跨账号同目标的重复检查仍生效。只有 Verified、未过期、疑似故障类别才影响站点过滤。

UC-08 审核问题报告

主流程：查看证据、理由、revision 与审计

  1. Moderator 打开 Report review → Refresh → 找到主线 Fast 报告 → Review。查看说明、图片、相关报告、官方缓存状态与审计历史。合成站点找不到真实 LTA 状态是正常情况，不要把缓存状态说成实时查询。
  2. Decision action 选 Verify，Decision reason 输入“演示审核：已核对合成报告证据。”，点 Record decision。
  3. 看到 Verified、revision 增加、新审计条目。成功后弹窗保持打开；不是自动关闭。Driver 只有主动创建／重配／刷新后才看到新的过滤结果，旧版本不会被重写。
  4. 需要终态动作时按下表分别使用不同报告。Verify 没有破坏性确认框；Reject、Merge、Resolve、Expire 需要确认。
动作用哪条报告／操作合法结果
Verify主线 Fast 疑似故障报告；Pending、未过期。Pending → Verified，产生故障支持。
Resolve上面同一条 Verified Fast 报告。Verified → Resolved；无其他支持时下一次计算恢复该站。Pending 也可 Resolve。
RejectUC-07.A1 的 Value / Blocked charging bay Pending 报告。Pending → Rejected；说明证据不足等理由。
Expire另建 Reported Fault / Access problem 的 Pending 报告，立即用 Expire。Pending 或 Verified → Expired；不用现场等 24 小时。此非故障类别不影响候选。
MergeDriver B 用 pp.seedMerge() 预备同站同类、不同合成连接器的两条 Pending 报告。Review 来源 A → Merge → Canonical report 选 B → 填理由 → 确认。来源 → Merged，保留目标；不是把两条故障支持简单相加。Verified 来源只能并入有效 Verified 目标。
Flow具体操作应看到／恢复方式
UC-08.A1 取消填入理由但不提交，关闭 Review 或按 Escape。原状态和审计条目数量保持。重新打开可核对。
UC-08.A2 Merge按上表使用两条同站同类别的有效报告。来源为 Merged，目标保持规范记录；不要把不同站点／类别强行合并。
UC-08.A3 证据矛盾对 Pending 的非故障演示报告 Reject；或对已解决的问题 Resolve。理由记录在审计历史中。没有其他有效 Verified 故障支持时才解除站点排除。
UC-08.A4 缺少理由／目标空理由时提交；Merge 时选择空的 Canonical report 再提交。必填校验阻止操作，无新审计。UI 理由至少 3 字符，示例用完整句子。
UC-08.E1 revision 冲突M1、M2 两个隔离会话同时打开同一条 Pending 报告，保持相同 revision。M1 先 Verify；M2 不刷新，用旧弹窗再提交。M2 的真实请求为 HTTP 409；弹窗保留错误，不自动 reload。关闭 → Refresh 列表 → 重新 Review 才拿到新 revision；旧请求未追加第二条决策。
UC-08.E2 越权Driver 无 Report review 入口；在 Driver 会话执行附录的 report.moderate 请求。服务端返回 403；不能只用“没按钮”来证明后端权限。
UC-08.E3 保存失败在 Moderator 上 pp.failNext("report.moderate")，填理由再提交。受控 503，原报告／审计不变，理由仍可重试。请求未到后端；不据此宣称已测试数据库异常回滚。

不要在同一条报告上按顺序点五个动作。Rejected、Merged、Resolved、Expired 是终态；切换到另一条适合该动作的报告。所有演示报告在类别、连接器和编号上要能辨认。

补充场景 无备选和同站多个故障支持

1 稳定展示 UC-06.E2 没有备选

  1. 先恢复固定基线，确保 A 的主线计划当前有 Fast、Reported Fault、Value 三项，并选 Fast。核心 Fast 报告若已 Resolved，可以再准备新报告。
  2. Driver B 从这三个卡片各提交一条 Suspected faulty connector，说明写“2026-10-29 无备选演示”。每提交一次会转 Reports，从 Saved plans 重开基线继续；先不刷新掉候选。
  3. Moderator 将这三条新报告逐条 Verify。Driver 回此前计划 Refresh data：三项都被故障过滤，显示没有可行备选、旧选择清空。
  4. 固定参数下只需这三个可行候选，不需要给全部九个样例站点都建报告。若放宽绕行、改变时间或车辆参数使其他站也可行，应先恢复固定基线。
  5. Moderator Resolve 本次三条报告，再 Refresh，恢复三项。Driver B 若已用两次 Merge 准备，再建三次正好耗满 5 次；后续报告换专用账号。

2 同站两条支持并存（额外验证）

  1. 在额外新 Driver 的 Console 载入工具，pp.seedSupports() 创建两条针对 Fast、不同合成连接器的疑似故障报告；Moderator 分别 Verify。
  2. 刷新基线：Fast 被排除。只 Resolve 其中一条，再刷新：Fast 仍被另一条有效支持排除。
  3. Resolve 最后一条，再刷新：Fast 恢复。这里展示的是同站多条支持的逻辑，不把合成连接器说成真实 LTA 设备。

辅助操作 没有正常界面入口的分支

1 载入工具和查看状态

只在本机演示应用、专用账号下使用。打开 DevTools Console，将 demo-support/demo-console.js 的全文粘贴一次。它只定义 pp 工具，不会自动创建数据；每个隔离浏览器会话各自载入。不要打印本地会话或 access token；Network 演示看 Status / Response 即可。

// 读取当前账号的资料和自有计划（没有写入）
window.demoBoot = await pp.api('bootstrap');
console.table(demoBoot.plans.map(p => ({
  id: p.id, title: p.title, versions: p.versions.length
})));

// Driver B 预备 Merge：两条 Pending 合成连接器报告，消耗两次额度
await pp.seedMerge();

// 仅额外 Driver：两条疑似故障支持，消耗两次额度
await pp.seedSupports();

// 限流专用 Driver C：先在 UI 建好车辆和计划
await pp.rateDemo();

seedMerge/seedSupports 会打印完整 ID 和前八位编号，方便在审核列表辨认；只有后续 Moderator Verify 才会使疑似故障影响推荐。主线默认单连接器 + 全局去重，无法靠普通报告 UI 稳定造出 Merge 所需的第二条同站同类别记录，所以这两条是明确的准备数据。

2 真正的服务端校验和权限拒绝

// UC-02.E1：Driver 已有合法 profile 时，服务端应拒绝 9 kWh
window.demoProfile = (await pp.api('bootstrap')).profile;
await pp.api('profile.save', {
  profile: { ...demoProfile, capacityKWh: 9 }
}); // 预期 HTTP 400；合法 profile 不被覆盖

// UC-04.E1：在 Driver B 窗口，替换为 A 事先记录的完整计划 UUID
await pp.api('plan.refresh', {
  planId: '替换为Driver A的完整计划UUID', mode: 'DEMO_FIXTURE'
}); // 预期 HTTP 404；短八位编号不是 UUID

// 不存在的计划：随机有效 UUID，预期 HTTP 404
await pp.api('plan.refresh', {
  planId: crypto.randomUUID(), mode: 'DEMO_FIXTURE'
});

// UC-08.E2：在 Driver 窗口调用，角色校验应先返回 HTTP 403
await pp.api('report.moderate', {});

上面的请求逐条执行；预期错误会在 Console 抛出，避免把整块连续粘贴后第一条错误中断误认为后面也已执行。角色检查先于该审核操作的业务参数校验，所以最后一条不需要真的改动任何报告。

3 受控界面请求失败与恢复

// 每次选一个动作，然后回 UI 点对应按钮：
pp.failNext('profile.save');       // Save vehicle
pp.failNext('plan.create');        // Find charging options
pp.failNext('plan.select');        // Choose this stop / Select charger
pp.failNext('plan.reconfigure');   // Recalculate plan 或策略标签
pp.failNext('plan.refresh');       // Refresh data
pp.failNext('report.create');      // Confirm & submit report
pp.failNext('report.moderate');    // Record decision

// 若还没点按钮就要取消模拟，手动恢复：
pp.restore();

不要一次执行七条 failNext：后面的设置会覆盖前面的。每次只设置一个，命中一次指定业务请求后自动恢复；随后再点同一按钮即正常重试。它只影响当前浏览器窗口，不改变真实账号角色、数据库或服务器环境。

4 Auth 和上传失败

认证：页面加载后把浏览器网络设 Offline，再尝试 Sign in，完成后立刻改回 Online。图片上传：在 Network 的 Request blocking 中只阻断目标 Supabase Storage 上传路径（通常包含 /storage/v1/object/issue-images/），点带图片的 Submit，展示保留输入的上传错误，再解除阻断重试。不要把浏览器阻断 OneMap URL 当成服务器端 OneMap 调用失败。

演示收尾和答问提示

收尾顺序

  1. Moderator 把本次演示创建、仍有效的 Verified 故障报告 Resolve 或 Expire；两条支持要分别处理。Pending 演示报告也转终态，避免下次全局去重挡住同目标提交。保留审计历史。
  2. Driver 恢复固定基线并刷新，确认三项恢复。这里确认的是本次故障支持已解除；不要批量清理其他人的记录。
  3. 在 Saved plans 删除准备好的可丢弃计划，确认它和所有版本从列表消失；不要误删还要展示的基线。
  4. 按 UC-02.A2 删除车辆，确认无当前 profile 时不能新建计划，但剩余保存计划仍能查看旧假设。需要留下一份可继续演示的工作区时重新保存基准车辆。
  5. 取消所有 DevTools 阻断／Offline／pp.failNext，恢复 Online；最后各账号 Sign out。
老师可能问可直接说明
为什么不是充满 100%？自动目标覆盖站点到终点所需能量，再加车辆配置的储备；手动目标仍受可达性和时间限制。
为什么选择推荐不生成版本？选择是计划层的可变偏好；计算结果才是不可变版本。重配和刷新成功会追加版本。
为什么 Pending 不过滤？未经审核的用户报告不能直接排除站点。只有有效、未过期的 Verified 疑似故障支持才参与过滤。
为什么一条报告解决后站点还被排除？同站可能还有另一条有效支持；必须检查关联报告，不能只看某一条的终态。
先过滤还是先排名？先按可行性和策略形成排序，之后去除被有效审核故障标记的站点，最后取最多三项。
Demo 的日期为什么是旧的？固定夹具保留固定来源时间，用于重复演示。Live 的真实来源时间和过期状态单独显示；Demo 不声称实时。
为什么 Demo 仍要网络？合成的是 provider 数据。账号、保存、私有图片和审核仍使用 Supabase；地图瓦片也可能联网。
Price unavailable 是免费吗？不是。缺少或不支持的单价不会当成零元参与费用说明。
五个策略为什么有时排得一样？数据可能在某些指标上相同；策略不同不保证每次排序都不同，尤其可用比例全部相同。
是否预订或预测到站一定有空位？提供带来源时间、假设和解释的建议；没有预订、支付、排队或未来可用概率保证。
现场出现故障怎么办？先保留当前输入／旧版本，看实际错误。解除受控阻断；若真实 provider 不可用，明确切换到 Demo 继续业务主线，而不是把 Demo 说成 Live。
