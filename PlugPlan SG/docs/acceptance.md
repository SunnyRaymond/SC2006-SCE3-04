# PlugPlan SG acceptance plan

This document maps the agreed 25 functional requirements, eight use cases, and ten non-functional requirements to the implementation and evidence needed for acceptance. The canonical use-case descriptions are in [`../../lab2/source/use_cases.json`](../../lab2/source/use_cases.json); FR/NFR wording is in [`../../Lab 1/source/build_srs.py`](../../Lab%201/source/build_srs.py).

## Status and test setup

`Verified` means the stated behavior has direct evidence in the dated execution record. `Regression verified; approval pending` means calculation regressions pass but the team has not approved the fixed fixture/oracle set. `Pending` means required external or human evidence has not been collected. See [verification.md](verification.md) for run details. The final production-build browser suite passed 8/8, including the duplicate and HTTP 429 UI branches. All nine axe frames had zero serious/critical violations. The remaining acceptance gates are NFR-04 team approval, NFR-05 HTTPS/TLS inspection (deferred by the owner until deployment), and the NFR-09 study with five real first-time users.

Use a dedicated Driver and Moderator from the private `PlugPlan SG/.local/test-users.json` created for integration testing. Do not copy credentials or tokens into this document, SQL, screenshots, source control, or test output. These test accounts are not usability-study participants.

From `PlugPlan SG/`, run the project checks:

```powershell
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
```

For browser acceptance, use the ignored `credentials.env`, start `pnpm dev`, and use dedicated accounts from the private test file. Course-demo registration is configured without email confirmation; real UI signup, password sign-in, and the default DRIVER role were verified. Google/GitHub provider configuration is deferred by the owner, and inactive providers are hidden. The implemented UC-01 account flow is registration, sign-in, and sign-out.

Database-level RLS/RPC checks already passed in rollback transactions against the target project. Run destructive checks only with dedicated test accounts. Scripts clean up their generated plans; report audit records are preserved in terminal lifecycle states after verification. The current SQL makes report expiry effective for fault filtering by timestamp; it does not run a background job that rewrites an expired row's status to `EXPIRED`.

### NFR-01 benchmark record

[`../scripts/benchmark.mjs`](../scripts/benchmark.mjs) is the controlled 20-Driver/100-request runner. Running it without `--run` prints usage only. Run it against the intended Node server only when you explicitly opt in with `--run`. A local server started in production mode is a valid performance target; deployment is not required. For example:

```powershell
node scripts/benchmark.mjs --run --mode=live --server=production --base-url=http://127.0.0.1:3000
```

Loopback HTTP is allowed for this benchmark, including with `--server=production`; external hosts must use HTTPS. The runner records the URL scheme but does not inspect the negotiated TLS protocol, so neither a local nor remote benchmark is NFR-05 TLS evidence. Verify deployed HTTPS/TLS separately for NFR-05.

The runner reads the 20 Driver records from ignored `.local/test-users.json`, sets the defined default profile, and warms one real LIVE NTU-to-Marina plan per Driver sequentially with a five-second gap. It starts the formal run only after all 20 sign-ins, profile saves, and warmup plans succeed with cached or fresh source data. It then runs five strategy-only `plan.reconfigure` requests per Driver at concurrency 20. All 100 attempted responses, including failures and slow responses, stay in the denominator. Only the plans created by this runner are deleted, using each owner's API access; it does not sign out the accounts or delete other user data.

The redacted result is written to ignored `.local/performance.json` and includes the server environment, Node version, target scheme/scope, workload, each formal request's latency/status/source age/state, p50/p95/max, and cleanup counts. It stores no account identifiers, passwords, or tokens. `--mode=fixture` may be used for diagnostics but always reports `DIAGNOSTIC_ONLY` and cannot satisfy NFR-01. If any LIVE warmup fails or cannot establish cached/fresh provider data, the record is `INSUFFICIENT_DATA` and the 100-request run is skipped. **Benchmark status: PASS on the final production build (100/100 HTTP 200 at 20 concurrent users; p95 1,918.67 ms; maximum 2,033.83 ms; all 20 generated plans cleaned up). See verification.md.**

### NFR-10 reliability record

[`../scripts/reliability.mjs`](../scripts/reliability.mjs) is the controlled 100-journey API runner. It makes no network calls unless passed `--run`; it reads exactly one dedicated Driver from the private ignored `.local/test-users.json` property `reliabilityUser`. It runs against `DEMO_FIXTURE` and does not use provider data. Use `--run` to explicitly opt in to the disposable-account API verification.

```powershell
node scripts/reliability.mjs --run --server=production --base-url=http://127.0.0.1:3000
```

Each journey records create, compare, select, refresh, reconfigure, delete and deletion-verification statuses. It requires exactly three recommendations with finite numeric values, explicit `DEMO_FIXTURE` provenance, append-only version progression and unchanged older result copies. There are exactly 100 reconfigure requests, cycling through `FASTEST`, `CHEAPEST`, `AVAILABILITY`, `DETOUR`, and `BALANCED`. Failed attempts remain in the 100-journey report; runs blocked before journey execution remain explicitly `NOT_RUN`, so they cannot be reported as a pass. Only uniquely titled plans created by this runner are deleted, and the account's original vehicle profile is restored. The script does not sign the account out or change unrelated data.

The redacted record is written to ignored `.local/reliability.json`; it contains no account identifiers, credentials, tokens, plan IDs or response bodies. A `PASS` is only the journey gate. `pnpm test:coverage` must still be run independently to assess branch coverage for the named modules. **Reliability status: PASS on the final production build (100/100 journeys; zero failures/skips; cleanup 100/100; profile restored; all four logical partitions above 80%). See verification.md.**
