# PlugPlan SG system description supplied to the AI

PlugPlan SG is an arrival-aware EV charging recommendation web application for SC2006 Team SCE3-04. Its Lab1 baseline has 25 functional requirements, 10 nonfunctional requirements and eight use cases. Drivers register and authenticate, maintain one vehicle profile, create a charging plan, compare recommendations, reconfigure a plan, manually refresh for a fallback and submit charger issue reports. Moderators authenticate and verify, reject, merge, resolve or expire reports with an auditable reason and timestamp. Moderator accounts are provisioned; public registration creates Driver accounts.

A plan combines usable battery capacity, consumption, compatible plugs, AC/DC charging limits and reserve SOC with origin, destination, current SOC, departure time, dwell time, detour limit, a fixed ranking preset and an optional manual target. OneMap provides place and route information; an LTA DataMall backend adapter provides the latest usable station/connector snapshot. Live access and exact provider coverage still require a smoke test. Cached, stale and deterministic Demo Fixture data are labelled explicitly.

The recommendation engine checks reachability, connector compatibility, opening hours, detour and dwell feasibility. It calculates arrival SOC, an automatic charge-enough target to reach the destination with reserve, required charging energy, estimated charging time and supported per-kWh or per-hour cost. Missing or unsupported prices display Price unavailable. The fixed presets are Fastest overall journey, Cheapest charging, Availability-first, Minimum detour and Balanced. Availability-first is not a probability forecast. Results expose assumptions, source timestamps and explanations; two or three alternatives can be compared when available. Reconfiguration and manual refresh create immutable Plan Versions; old versions retain their inputs and evidence.

The sole agreed Lab1 scope refinement is FR-24 / UC-07: after the algorithm produces charging-station suggestions, stations marked faulty by Moderators are filtered out before the displayed shortlist. This applies to creation, reconfiguration and manual refresh. A Driver's raw Pending report cannot exclude a station. Other Drivers benefit through the filtered recommendations. A station with a Moderator-verified, unexpired fault report is marked faulty; resolution/expiry removes that report's support, and any remaining active verified fault keeps the station excluded. The result may contain only one or zero eligible options; it must explain this without recommending a marked station. This refinement does not create continuous monitoring or automatic alerts.

The product provides estimates and decision support only. Reservation, payment, remote charger control, queue coordination, telemetry and guaranteed availability are outside scope. Provider secrets stay on the backend. Required qualities include role authorization, salted password hashes, TLS, data freshness labels, profile/plan deletion privacy, keyboard accessibility, deterministic tests and low-latency cached recommendations. The reference environment and implemented performance have not yet been measured. Team technology experience has not been supplied and must not be invented.

Source material: Lab 1/Deliverables.docx and Lab 1/source/build_srs.py; user-approved FR-24 / UC-07 clarification; lab2/source/use_cases.json. The conceptual diagram is an analysis model, not a fixed implementation architecture.
